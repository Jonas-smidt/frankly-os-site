Welcome to Frankly OS.

The machine that remembers, so you don't have to start from scratch.

This is our internal workshop: it builds things, keeps what it learned, and gets a little better every time. You are teammate number two. Nothing here is finished, and that is the point.

Nothing it does is public by itself. Publishing and approving are human acts, and they are Jonas's.

The three things you will meet

Boot

Start every session by booting. One command loads everything the machine already knows — health, the active batch, the decisions waiting for Jonas, what ran overnight. Read it before you ask a single question; most of your questions are already answered on that screen.

python3 "/Users/jonas/Documents/Frankly os/os-visualization/scripts/frankly-os-boot.py" --quick (your clone's path once you have one)

The crew

You are not alone in here. Twenty-seven seats, each with one job, one contract and one clear stop rule. You scope the work and hand it out; the seats do the lifting and report back. If a seat says it cannot do something, that is the system working, not a bug.

The close

The way we work has three beats: build, learn, compound. You build something real, the machine writes down what it learned, and the next build starts from there. That is why the boring closing steps matter — the lesson you skip is the mistake someone repeats.

How a task flows

The gate is the only amber object on purpose: it is the only place work can stop. The dashed line is the learning returning — the loop is supervised, not autonomous.

Five steps to your first run

  1. Clone the repo (ask Jonas for access): git clone <frankly-os-maskinen url> "Frankly os"
  2. Run the setup script from your clone: bash tools/setup-teammate.sh — read what it prints; add --yes-hooks when you are ready for it to wire the session hooks into your ~/.claude/settings.json (it shows the exact change first).
  3. Open Claude Code in the repo. The hooks boot the OS for you; the crew skill lives at .claude/skills/frankly-crew/ and loads automatically.
  4. Read the governance file — the tracked copy is at os-visualization/system-intelligence/CLAUDE.md. It is the contract for how we work; the gates in it bind you and the machine alike.
  5. Do your first run. Every run closes with a run-card and a lesson — the Stop hook walks you through it. That close IS the work being saved.

The page you are reading re-presents ONBOARDING.md in the machine repo — that file stays the source of truth; if the two drift, the file is right.

Your first week: one bounded mission

You get one mission, not a backlog. It is finished when the stop rule fires, and then you stop.

Mission: ship one small, real change to the internal Lab surface, supervised end to end.

Day 1 — Get the machine on your machine

Clone the private machine repo (ask Jonas for access; do not improvise a location). Boot it, every session, before anything else, and read what it prints: health, active batch, decisions waiting for Jonas, next best action. Then read the governance file end to end. It overrides your instincts. The parts to know cold: the gates, the deletion rule (never delete, move to _retired/), the version rule (+0.1 per OS-changing run), English at source.

Day 2–3 — Your first supervised run

Ask the machine what it already learned about your topic: python3 os-visualization/scripts/build-lessons-index.py --query "<your topic>". Build through the crew, not by hand — if the skill will not load, read the seat file in .claude/agents/ and brief a real subagent with it, and say out loud which lane you are in. Check yourself with python3 os-visualization/scripts/run-frankly-os-evals.py, then close the run with python3 os-visualization/scripts/record-frankly-run.py — at least --agent-used M1, plus the lessons you learned.

Stop rules — non-negotiable, whichever comes first

  • Green evals + a recorded run-card: done. Stop and report.
  • Any gate reached: connector/Drive write, paid API, plugin install, anything touching franklyinsure.com, or claims/product/legal wording outside _scratch/. Stop and hand back to Jonas.
  • Second failed attempt at the same fix: stop, write down what you learned, ask.
  • End of week regardless of state: stop and report honestly. An unfinished mission described accurately beats a finished one described vaguely.

Nothing runs in the background on your behalf. If it is running, someone chose it.

How work flows: routes

A route is a written recipe for one kind of work. It names the goal, what it needs as input, the steps in order, the quality door the result must pass, when to stop, and what to hand back to Jonas instead of deciding yourself. Every route ends with "Lessons From Use" — the notes earlier runs left behind — so you read the route before you start and add to it when you finish. Twenty routes live in os-visualization/routes/. If your task doesn't fit one, that's a signal, not a shortcut: say so before building.

The three routes a newcomer meets first

  • website-publishing-workflow-route.md — any page, Lab surface or landing draft. Six steps: Context → Layout translation → Content draft → Visual QA → SEO QA → Publish or park. Start from the git-tracked frankly-os-site/ repo, never the Drive copies (they are stale).
  • system-maintenance-route.md — keeping the OS healthy. Run janitor.py (dry-run by default, --apply to fix). It never decides anything for Jonas.
  • system-visualization-route.md — decks and system visuals. Read its one-pass runbook at the top, and run preflight-visual-run.py before building; it exits 1 until the plan, reference, method card, asset inventory and format are in place.

Working with partners

Partner work has its own rails. Read them before you touch anything a partner will see.

The one rule. Nothing partner-facing, customer-facing or checkout-facing goes out until Jonas plus the product/legal owner plus the partner owner approve it. The partner activation route says this in its own words and has stayed test-next since 2026-07-08 for exactly that reason. No real partner pilot has run yet.

What is showable. Internally: kit structures, audience splits, seller-usefulness reviews, 1–90 day activation plans, missing-source lists, approval checklists. You can build all of that today.

What is gated. Approved product descriptions, coverage explanations, checkout copy, commercial terms, launch templates, logo/brand usage rules, and any live partner communication. Also: Slack posts, Drive writes, paid tools, and public deploy to franklyinsure.com. If you are unsure whether a sentence is a claim, treat it as one.

How to work when a fact is missing. Record it as a gap. Never invent a product fact, a price, a coverage detail or a commercial proof point to make a draft feel finished. "Gap, not guess" is the whole method.

Where partner material lives. Route: os-visualization/routes/partner-activation-route.md (activation + kit structure) and partner-case-study-route.md. Heavy partner assets — logos, film, deck zips — live in Drive; text deliverables live in this repo.

Two things past runs learned the hard way. Frankly-authored partner copy is written in English even when the partner's own slogan is Danish (verbatim quotes with attribution and proper product names are the exception). And "the logo" is not one field when a partner has both a wordmark and a compact mark — name assets after what they are, and let a missing asset fail visibly rather than silently falling back to type.

Rules that bind from day one

Most of what you do needs no permission — build it, check it, log it, keep going. A short list is different: anything that leaves this machine, costs money, or touches the real customer site stops and goes to Jonas. Product and legal wording stays off-limits until he opens it by name. The gates are not distrust. They are the reason the rest is open.

  • Nothing is deleted — ever. Superseded files move to _retired/<date>-<why>/.
  • Claims / product / legal content is LOCKED everywhere except one lane: _scratch/ is your private, local, gitignored workspace — anything there never leaves your machine by any automated path. Moving content OUT of _scratch/ is a human act and it goes to Jonas.
  • English at source. Everything new is written in English (history stays Danish).
  • Only Jonas approves. Improvements, new agents, and merges to main are proposed by you and approved by him. Work on a branch; he merges.
  • Say what lane you are in. If a tool or skill is unavailable, say so on the first turn — never silently hand-execute what should have been staffed.

Four things you never do alone

  • Money: any paid API call goes to Jonas. Code-enforced.
  • Anything that leaves this machine: Drive/connector writes, Slack posts, plugin installs, auto-created threads, git push to remotes. Jonas. Code-enforced.
  • The real site: franklyinsure.com is human-supervised, permanently. os.franklydesign.dk is our internal test surface and is open — build, fix, push, deploy, then say plainly what went out. This split lives in prose (the governance file), not in the classifier — the governance file is the authority.
  • Claims, product, coverage, legal wording: locked everywhere except _scratch/, which is free. The classifier's verdicts are hints, verb-dependent, and do not cover Danish — never quote one as permission.

Newcomer footnote: the tier charters (v0-2/v0-3) are mostly written, not wired — only verify-before-attest, terminal-is-terminal and deferred-goes-to-Future-Improvements are actually enforced by code. Never cite a charter as permission. And the cockpit approve button is Jonas's hand only.

Ten facts about Frankly OS

Ten things that are true today, 2026-08-21. Every number here comes from a file the machine maintains — if it drifts, the file is right and this page is wrong.

  1. One home. The private machine repo is the home: knowledge in canon/, the operating layer in os-visualization/. Drive is the archive, the home for heavy files, and one live write lane — the brain/ feedback inbox. If the repo and Drive disagree, the repo is right.
  2. Version 6.21, as of 2026-08-21. The single source is os-visualization/system-intelligence/os-version.json, field version. Never hardcode it anywhere — read it. Every run that changes the OS bumps it +0.1; major numbers only when Jonas names them (6.0 = "One home").
  3. Boot before you build. The boot script prints health, the active batch, what is waiting for Jonas, and the next best action. It replaces asking 200 questions.
  4. One surface. The cockpit at http://127.0.0.1:8137/frankly-os-cockpit.html is the only UI. Decisions get approved there — every attempt, including refusals, is audited.
  5. A crew of 27 seats, tiered by responsibility (contract v0-26). Full-crew runs are rare, so cost exposure is bounded; the daily token meter is the named watch instrument.
  6. Never delete — move. Retired things go to _retired/<date>-<why>/. Nothing is removed until the system is proven to work without it. Applies to git rm too: untrack and move.
  7. Tighten freely, loosen only with Jonas. Making a check, test, gate or eval stricter is your own call; loosening one is Jonas's. A stricter test cannot hide a fault; a looser one can.
  8. Two deploy targets, two rules. os.franklydesign.dk is the internal test surface and is open — build, fix, push, deploy, then say plainly what went out. franklyinsure.com is the real site and never moves without Jonas.
  9. Claims, product and legal are LOCKED — with one open lane. Inside _scratch/ that work is free, because the wall is the directory. Getting anything OUT is a human act and goes to Jonas.
  10. The loop compounds. Every run reads the matching lessons first and files new ones back; 60/60 evals and a green self-check as of 6.20/6.21. If you solve something by hand in the chat instead, say so and say what got skipped — the silence is the failure, not the shortcut.
